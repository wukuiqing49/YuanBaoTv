# Zeplin 实施流程

## 分析输出

用户未明确要求编码时，实施前使用以下结构输出：

```text
页面：<名称>，<画板宽>x<高>，<变体>
层级：<根节点 -> 分区 -> 可复用组件>
导航与状态：<Activity/Fragment、路由、UI State、列表>
图层映射：<重要图层 -> Android View/资源>
资产：<已有、需导出、格式、落地路径>
资源：<strings、colors、dimens、drawables、语言>
待确认项：<缺失行为、后端契约、注释冲突>
```

## 实施顺序

1. 确认目标页面/组件和范围。
2. 检查现有等效 UI、路由目标和资源模块。
3. 获取 Zeplin 图层与 Token，处理组件复用和资产。
4. 先添加资源，再实现布局，最后接入 Activity/Fragment 行为和状态。
5. 只接入设计、注释或既有产品流程能够证明的交互。
6. 交付前构建并进行视觉对比。

## 视觉验证

1. 使用与 Zeplin 画板宽度对应的 Android 视口运行页面，并至少增加一个更小的 Android 视口；记录设备尺寸、密度、系统栏模式和字体缩放设置。
2. 对每个视口保存运行截图，与 Zeplin 预览逐区对照：状态栏和导航栏 Insets、文本内容与换行、边缘和基线对齐、间距、颜色、圆角、图片宽高比以及裁切方式。
3. 对设计中明确存在的默认、按压、选中、禁用、加载或错误状态逐一核对；设计未定义的状态不要虚构。
4. 对差异按“已修复”“平台/系统差异”“设计数据缺失”“依赖未就绪”记录原因与影响。是否可接受应依据设计意图、现有项目规范和用户确认，不使用脱离项目背景的统一像素阈值。
5. 没有 Zeplin 预览、无法运行构建或未取得对应状态时，明确列出未验证项，不得宣称像素级还原。

## 交付输出

```text
修改文件：<路径>
新增资产：<路径与来源图层>
资源/语言：<摘要>
行为：<路由、状态、后端调用>
验证：<构建/测试/视觉结果>
视觉差异：<视口、差异、原因、处理结论>
待处理依赖：<服务端配置、凭据、缺失状态>
```
